## What I read today
- BackendForge (arXiv 2607.11042, EMNLP 2026 Findings). A benchmark of 56 backend tasks rewritten from real open-source apps. Each task gives a visible spec.md and an openapi.yaml. The model must deliver a Python service plus a Dockerfile. A hidden HTTP test oracle (7,890 pytest items, about 24,800 requests) then checks the running service without reading its code. A task passes only if every oracle item passes. Best result was GPT-5.5 at 28.57% on the final oracle. Most failures were validation, followed by authorization, state, side effects and workflows. The page says the artifacts are not released yet; the authors only say they intend to release them. (https://arxiv.org/html/2607.11042)
- ABC-Bench (arXiv 2601.11077, ACL 2026 Findings), from OpenMOSS and Fudan. It has 224 backend tasks from open-source repos, across 8 languages and 19 frameworks. Agents have to explore the repo, build and run a containerized service, and pass external end-to-end API tests. The code and harness are on GitHub (OpenMOSS/ABC-Bench) and the dataset is on Hugging Face. A third-party summary (not checked against the paper) says the best model reached 63.2% pass@1 and that environment setup was the main bottleneck. (https://github.com/OpenMOSS/ABC-Bench)
- BaxBench (ETH Zurich, ICML 2025 spotlight). It has 392 backend tasks (28 scenarios across 14 frameworks in 6 languages). Each task runs in Docker with functional tests and end-to-end security exploits. The best model was right about 62% of the time, and exploits worked against roughly half of the correct programs. Models also did worse on less popular frameworks. (https://arxiv.org/abs/2502.11844)
- Schemathesis. An MIT-licensed Python tool, built on Hypothesis, that generates property-based tests from an OpenAPI or GraphQL schema. It also supports stateful tests: chains of requests where each one builds on the previous result, using OpenAPI links. You can run it from the CLI (for example `uvx schemathesis run <url>/openapi.json`), as a pytest decorator, or in CI. (https://schemathesis.readthedocs.io/)
- FastAPI's TestClient, documented in the official testing tutorial. It is based on HTTPX and comes from Starlette. It tests a FastAPI app without opening a real HTTP socket. Tests are plain pytest functions with normal, non-async calls. The docs also cover headers, and the advanced section covers async tests. (https://fastapi.tiangolo.com/tutorial/testing/)

What is missing is a planner that writes web tasks and HTTP tests, and a `start` that marks the product as web. ## What could go wrong
- Old products change by accident. With web=False, the planner prompt and the files written must stay exactly as they are today.
- Hidden tests from all tasks run together against ONE running service, so data from one test stays in the service for the next. If the planner's tests assume an empty store or fixed ids, they fail at random. The web rules must ask for unique data in each test and forbid assuming an empty store.
- urllib.request raises HTTPError for 4xx and 5xx answers. If the planner's tests don't expect this, every error-case test crashes. The web rules must say how to read the status code from HTTPError.
- The builder agent runs its own tests without PRODUCT_URL. If its tests need a running server, they fail in its workspace. The web rules must tell each task to test the app in-process by calling `application` with `wsgiref.util.setup_testing_defaults`.
- Without a starting app, task 1's judge run would end with 'could not run' before the agent even starts. The web starting app must exist and answer 404 with JSON.
- write_plan overwrites an existing product, or leaves half a folder behind when the plan is bad. It must check everything before it writes anything.
- Moving code out of start() breaks start(): idea.md is missing, or the planner call changes. start must still call subprocess.run once, with --system-prompt set to planner_prompt(web).
- The existing tests in tests/ must still pass. Do not change or weaken them.

## What the builder said
I added `--web` support to `factory.py`, and all 55 tests pass with `python3 -m pytest -q`.

- **`planner_prompt(web)`:** returns `PLANNER` unchanged by default. With `web=True` it keeps the intro and the task rules but swaps in web product rules: a JSON API written as a plain WSGI app, `application` in `app/web.py` served as `app.web:application`, the builder tests in-process with `setup_testing_defaults`, hidden tests use only HTTP via `PRODUCT_URL`, one shared service so tests use unique data, and hidden tests never import `app`.
- **`write_plan(product, plan, name, web)`:** the folder-writing part of `start()` now lives here and returns the task folders in order. It raises `FileExistsError` or `ValueError` before creating anything. With `web=True` it also writes `web.txt`, a starter `app/web.py` that answers 404 JSON to every request, a two-test `test_start.py`, and a README sentence about `app.web:application`.
- **`start()`:** sends `planner_prompt(web)` to the planner and adds a "web API" sentence to the planner's input. It then calls `write_plan`, writes `idea.md` and prints the tasks from the returned folders.
- **Flag and docs:** I added the `--web` flag and one line about it to the usage text and to `README.md`.

If the planner sends back a badly shaped plan, `start()` now stops with the `ValueError` from `write_plan` rather than turning it into a friendly exit message, because the task didn't say which to do.

The new tests are in `tests/test_planner_web.py`. They cover the prompt text, both folder layouts, running the starter project's own tests, the 404 JSON answer, bad plans and existing folders (nothing written), and `start()` with a fake planner.
